# AI 分析工作台：双任务流设计与实际操作

## 设计理念

这个页面不是 P0/P1/P2/P3 的功能堆积，也不是强制 6 步向导。用户首先选择**提取 JD 要求**或**求职分析与学习规划**；一个 JD 批次内部才按「准备、导回、人工审核」顺序执行。AI 仍由用户手动使用网页端，不调用模型 API。

首页显示当前岗位库筛选范围、至少具有一项**有效已确认要求**的岗位数及待审核要求数，并列出最近的提取批次。注意：**有一条已确认要求不等于整份 JD 提取完整**，本地不自动给出虚假的 100% 完整覆盖度。

## 工作流 A：JD 提取与人工审核

1. **岗位库筛选**：先在「岗位库」设定企业档位、优先级等；分析工作台与导出仍使用同一筛选范围。
2. **准备数据**：进入「提取 JD 要求」，点击「导出最多 50 条待处理岗位」或「导出当前筛选全部 JD」，再点击同位置的「下载 AI 提取说明」。第一种会跳过没有 JD 变更、且已有正在处理/审过的提取批次的岗位。
3. **AI 网页端**：逐批上传完整 JD JSON 与 `jd-requirements-prompt.md`。ZIP 解压后一个 JSON 文件一个 `package_id`，切勿跨批拼接返回内容。
4. **导回**：返回 `{"package_id":"...","requirements":[...]}`，可点击「从文件导入 AI JSON」直接选择文件，也可粘贴。先预览参考资料再保存；参考资料需为 `jd_text` / `eligibility` 的逐字原文，否则整次保存被拒绝。
5. **人工审核**：当前批次列表支持逐条修订、确认、拒绝、批量处理；也可切换到「查看所有待审核要求」。确认后才会计入结构化 JD 需求统计。
6. **恢复批次**：返回首页「最近 JD 提取批次」或提取页「批次历史」点击「查看 / 继续」；数据与批次状态存储在本地 SQLite。状态包括等待 AI、待审核、候选已处理、JD 已变化、返回无新增候选及人工标记无候选。
7. **没有候选**：当 AI 确实返回空要求时，可明确点击「人工确认本批无候选」；不据此声称 JD 本身没有任职要求。若批次 JD 已修改或已导回内容，接口会拒绝该操作。

**特别说明**：过去已导入 P1 要求的旧版包会以「历史已导回批次」形式出现。软件不保存已导出的 JSON 副本；需要原文件请到「数据与集成」的最近导出位置寻找。如已丢失或 JD 改动，可选择原批次并点击「重新导出当前批次 JD」，生成新的 `package_id`；不会覆盖原批次和已有审核结果。保存失败后即使已产生批次记录，也可通过此操作恢复，不能复用旧 `package_id`。

## 工作流 B：求职分析与学习规划

进入「求职分析与学习规划」后，软件读取当前筛选岗位的 JD 确认要求覆盖情况：

- **精简版**：只包含已确认要求，不附 JD 原文。没有任何有效确认要求时禁止导出；部分岗位没有已确认要求时在导出前再次警告，用户可明确确认用于不完整样本分析。
- **完整版**：包含完整原始 JD，可以在尚未结构化提取时进行初步探索。软件说明此模式并非已经完成要求审核。
- 可逐条勾选真实的个人经历、作品或能力参考资料。未选择默认不导出个人资料。
- 下载匹配的 AI 分析提示词，在 AI 助手网页端分析，返回 `findings` JSON。可以选择 JSON 文件导入或粘贴，预览来源引用和过期警告之后保存。学习任务仍须用户手动采纳。

## 旧版通用分析

原「01 · 生成分析数据包」保留在「高级：旧版分析」里，支持基准包、增量对比和旧版导出选项，不强迫新用户理解这些概念。不会删除历史 `analysis_packages` 或 `analysis_findings`。

## 后端与数据安全

- 数据库 Schema 15 → 16，新增 `jd_extraction_batches`：只存关联 `analysis_packages.package_id`、导出时的 JD 版本哈希、用户人工空结果标识以及导回事件信息；不复制招聘全文或私密备注。
- `/api/workflow` 只读返回各岗位当前有效要求计数、过期要求数量和最近批次进度。
- 仅在 JD 提取流程**明确指定** `intent=jd_extraction` 导出岗位包时注册批次；岗位库普通 JSON 导出（默认 `general`）仍可用于存档或其他分析，不会产生虚假的“等待 AI”待办。原 P1 导回保存时记录真实返回事件，即使 AI 输出的候选全是历史重复项，也不会显示“等待 AI”。
- `/api/requirements?package_id=...` 精确按批次审核，原来的无批次查询仍兼容；其他岗位的候选要求不会混在所选批次中。
- `/api/workflow/batches/{package_id}/no-candidates` 只有手动触发、且没有已有导回结果、JD 未变化时可标记空候选。
- 完整 JSON 备份包括新批次表，旧数据库自动无损创建该表，用户原有岗位、要求、企业和学习任务不需要迁移或删除。

## 验收重点

1. 新用户只有岗位没有已确认要求：首页引导 JD 提取，精简版禁用，完整版可用。
2. 首批导出 30 条岗位和 AI 提取说明，获得一个或多个独立 JSON；逐批导回，核对 evidence 与相应 package_id。
3. 不同批次有待审要求：切换批次后只显示该批次记录，切换“全部待审核”显示整个库。
4. 同一岗位多次导出：全是重复要求的 AI 导回仍显示“已返回，无新增要求”，不会误报未处理。
5. JD 变更后：旧导出批次提示过期，不能以旧 JD 进行要求写入或标记空候选。
6. 完整的 JSON 文件导入：既支持 `requirements` 又支持 `findings`，手动编辑后必须重新预览。
7. 关闭重启 EXE：本地历史批次可恢复，最近待审核可继续操作，个人隐私默认不导出。
8. 旧版增量分析、P2 统计、岗位/企业 JSON 和新增的分页分支均不应受影响。

**代码合并不等于完成 Windows EXE 实机验收。** 必须在目标电脑运行 pytest、重新打包并操作以上场景才能宣称原生交付完成。
