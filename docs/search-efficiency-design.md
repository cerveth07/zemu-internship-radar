# 检索效率与成本控制

状态：v0.10.0 已落地实习僧列表/详情分段、指定身份续补、24 小时完整缓存、来源版本与实际访问回执；计划中的实习僧动作有累计访问额度约束。下文其余自适应调度、抽样新鲜度核验与跨轮探索仍为设计。操作及边界见 [分段采集与缓存](staged-collection.md)。

## 优化对象

减少重复平台访问、无收益的翻页、重复详情与无变化 JD 的处理，同时保留发现未知别名、低频路线和新招聘需求的机会。

不能只用「有效新增 / 搜索次数」决定所有动作。发现新机会、补齐缺失资料、核验缓存和确认来源变化各有收益，分别统计；待人工审核的岗位不当无效。耗时和请求数不等同于用户审核时间，界面另外显示待核对积压。

## 1. 列表发现与详情补全分开

第一段读取有限的列表页，保存可可靠读取的岗位 ID/链接、标题、城市、来源查询及时间；不要求每条候选立即打开详情。

第二段汇总候选身份，只给需要读取详情的候选排队：

1. 同平台同 ID 同轮只发起一次详情读取，所有查询命中都保留。
2. 有可用且未过期缓存的候选先复用，不因被另一个词命中就再次读取。
3. 明确下线或有可靠参考资料表明不满足硬性条件的候选可以降低详情优先级，保留发现记录。
4. 信息缺失、标题/城市乱码或列表没有资格字段时保持未知，不能提前排除。必要时先读取少量详情确认该页能否可靠解析。
5. 从剩余候选中按职业路线、个人约束、信息缺口和探索份额分配详情额度。未获额度的候选明确标成「未读详情」，可在后续继续，不假称完整采集。

列表读取本身也有成本；对需要打开详情才能读准字段的平台，两段式的优势必须实测，不预设一定便宜。

当前接口把列表和详情打包在一次采集里。实现时先增加连接器的列表发现/指定 ID 补详情能力及实际计数回执，再启用规划器；不能只在前端把一次完整采集改名为两段式。

## 2. 按信息缺口选择下一步

调度的候选动作是「某个词再读一页」「测试一个别名」「补一个候选的详情」或「核验一个来源」，每步完成后才决定下一步，避免先把每个词三页和全部详情额度都花掉。

| 看到的情况 | 优先考虑的动作 | 原因 |
| --- | --- | --- |
| 列表出现大量未见过的 ID，但详情额度有限 | 对新候选分配详情，暂缓继续搜别名 | 已有尚未评估的信息，不急着增加重复发现 |
| 代表词结果相关且本页有持续的新 ID | 试下一页，仍只读取获额度的详情 | 页深可能比同义词更有增量 |
| 已核验代表词偏离岗位族 | 测更具体的别名 | 改查询比扩大无关结果更有效 |
| 岗位族覆盖不足，当前词少量有效结果 | 给另一个别名或另一个来源小额度 | 少样本不能证明本词或岗位族已经穷尽 |
| 两个词在可比条件下长期重合 | 轮流搜索，降低同时出现频率 | 保留其历史独有命中和周期复测 |
| 所有来源受限或任务状态未知 | 停自动访问，保留队列，展示辅助入口 | 不通过重试耗尽额度，也不丢已有候选 |

同义词重合只能比较同平台、城市、过滤条件、相近时间和相近读取深度的实际 ID 集合。词义接近不等于结果相同；只看第一页也不能证明两个词完全等价。

P0 用固定轮转和明示理由做选择，P1 才根据审核反馈调整。初期可用「连续两轮成功读取但几乎没有新的 ID」作为降频提示，由规则参数或用户确认决定，不立即永久停用。

## 3. 缓存与新鲜度分别管理

缓存键至少包含来源平台、岗位 ID、内容指纹及解析规则版本。分别记录最后发现时间、最后详情读取时间和最后有效性核验时间。

- 新查询再次命中同一 ID 只追加命中记录；缓存不会因此自动变成「刚读取的详情」。
- 新 ID、缺少 JD、上次解析失败、确有来源变更信号或缓存到期时，优先补详情；发布日期/刷新时间变化只是核验线索，不证明 JD 已变。
- 待投递和临近截止的来源应优先核验；行业观察资料可低频刷新。阈值按实际稳定性设置，不先承诺一个适合所有平台的固定时效。
- 预留少量缓存抽样核验，检查即使列表没有变化的详情是否变更，避免长期沿用旧 JD。
- 只有连接器实测支持时才用更新时间、游标、条件请求或最新排序优化。没有这种能力时仍是有限页采样，不能宣称平台级全量增量同步。
- 原 JD 版本保留；同 ID 更新不算新岗位。解析规则升级先用已存原文重处理，只有参考资料不足才重新访问来源。

跨平台疑似同一招聘需求可以共用分类/推荐计算，但来源开放状态、截止时间及各来源内容独立核验，不能直接用另一平台的 JD 覆盖原来源。

## 4. 停止条件与覆盖保护

同轮重复页面、不可靠解析、达到额度或时间上限都可以停止当前动作，并记录原因。连续低增量可作为提前停止本轮页深的信号，定期保留更深页和稀有别名的小样本探索。

热门置顶、个性化排序和旧岗位可能占据第一页，因此第一页重复多不能推导后续页没有新岗位。早停表示本轮取舍，不表示搜索完成了来源全集。

探索按岗位族、平台与别名分散分配，避免把全部探索额度给同一组近义词。预算足够时至少保留一个探索动作；预算很小时明确展示尚未覆盖的路线和城市。

城市是用户约束，不能为省任务数擅自把多个目标城市改为「全国」。全国检索是否可替代城市检索，要同时核验覆盖和额外详情成本，并由用户选择。

## 5. 成本账本与审核反馈

分别记列表访问尝试、详情访问尝试、缓存命中、变化核验、失败/受限、重试、等待耗时与可选模型消耗。发生访问即记成本；缓存和本地重处理不伪装成平台访问。

全局预算包含发现、候选详情、探索、缓存核验及重试。每个平台有独立的访问间隔、限制状态和预检；复用已有浏览器会话，有限时间内复用准备状态，避免为每个词重新启动浏览器或重复重型预检。页面导航后仍检查实际访问限制。

示例预算仅用于说明：本轮 20 页列表、30 次详情尝试。列表可以先分 16 页主线、4 页探索；详情可预留 18 次新候选、4 次探索候选、4 次缓存核验和4次重试。所有部分合计仍是30次；未使用的保留额度可在规则允许时归还，不自动在轮末额外执行。配比需根据真实记录调整。

人工审核滞后时，分别显示新增候选、已审核有效和未审核；不因后者未知而降低某个词的收益。以找可投岗位为目标时，待核对积压达到用户设置上限可暂停继续补详情，优先消化已有资料；行业观察计划可选择继续积累。

原有 ChatGPT 数据桥仍可使用。若后续增加模型辅助，只处理新/变更且规则难以判断的 JD；按内容指纹、规则/模型版本及个人资料版本缓存结果，个人资料变化时重算匹配，不重新采集原文。每条结果都保留依据，未知资格不交给模型猜测。

## 6. 冷启动与验证

未测试的代表词或别名保留最小试探额度；只有成功、可比的搜索和足够审核结果才驱动降频或扩展。样本不足时显示参考资料不足；早期不做强化学习、复杂向量检索或隐藏的自动调参。

先用记录回放比较相同候选集上的旧流程与新流程，验证去重、缓存和额度是否真的少发了请求；再做范围受控的在线检查。来源随时间变化，在线结果差异不直接归因于优化策略。

验收至少包括：

- 三个别名命中同一 ID，只有一次详情访问，三个命中都保留。
- 下一轮再见到有效缓存的 ID，显示新命中与旧详情时间，按核验规则决定是否访问。
- 同一 JD 已变，能发现版本变化而不新增虚假岗位；解析版本变化优先本地重处理。
- 列表字段未知/乱码时不会被资格预筛误删；受限和解析失败不记为查询零收益。
- 少量总预算不会被一个热门词耗尽；探索、核验和重试不突破总额度。
- 重启续跑不重复读取已确认完成的动作；访问后未写回执的动作保持「结果未知」，核对后再决定是否重试。未读详情仍在候选队列，旧快照和人工判断可追溯。
- 记录新求职机会收益、更新/核验收益、审核完成率和成本；尚未探索的范围可见。

当前没有足够的长期历史数据量化节省比例或证明召回提升。先落实身份、两段队列、成本计数和缓存规则，再用实测收益决定扩展预算。

## 7. 用边际贡献判断扩展，不奖励重复命中

查询效果至少分成三个数：命中的来源记录、此前未见的来源记录、经审核确认的新求职机会。多个词都命中同一岗位时，各词保留命中，但本轮新增只算一次；跨平台关联未确认前，不把来源记录数当成机会数。

比较别名时，记录它相对已执行查询新增的 ID，以及历史上它独有的命中。先执行的词天然占据更多「首次发现」，因此首次发现归属不能直接证明哪个词更好。P1 可轮换代表词的执行顺序，在相同条件下比较有限页结果集合；后执行的查询因本轮预算不足而没执行，不记为零收益。

人工往往先审核标题吸引人的岗位，这会让已审核有效率偏高。统计须同时显示审核数、待审核数和样本来源；可以邀请用户核对少量不同路线、页深、查询的样本，未完成核对仍保持未知。未审核及硬性条件未知的岗位只用于观察发现增量，不作为已证实的有效新增。

重复率高也可能说明多个词都覆盖了重要岗位。因此降频依据应包含边际独有命中、最近成功检索时间、审核参考资料和覆盖缺口，不能仅凭重复率裁掉代表词。

## 8. 按当前瓶颈分配额度

保留明确的页数、详情次数和时间上限；不把这些成本换算成未经验证的统一分数。每轮先检查瓶颈，再用少量动作处理它：

| 当前瓶颈 | 本轮优先事项 | 何时切换 |
| --- | --- | --- |
| 未读详情很多，可判断的资料少 | 给不同岗位族的新候选补详情 | 候选不足或详情预算用尽 |
| 已读资料够多，待审核积压 | 达到用户设置上限时暂停补详情；继续提供审核入口 | 用户消化积压或调整上限 |
| 新机会很少且现有词已充分试探 | 测未探索岗位族、别名或来源 | 得到可评估候选或探索额度用尽 |
| 待投递岗位资料陈旧 | 优先核验这些来源，展示最后核验时间 | 到期候选已处理或核验额度用尽 |
| 平台受限、页面无法解析 | 暂停该平台自动队列，保留候选和辅助采集入口 | 用户处理或连接器恢复可靠解析 |

上述事项共享本轮总预算。额度允许时先给选中岗位族一次最小发现机会，再扩大高收益查询；如果预算连这一轮覆盖都不够，预览应列出本轮未探索范围，并跨轮轮转，不能承诺每轮覆盖所有组合。预留额度按小批次释放，避免早启动的查询长期占着未使用资源。

已知候选很多时仍保留有限的新词发现机会；积压控制按用户选择的求职或观察目标生效。查询表现应分平台、城市和过滤条件记录，不能把北京的历史效果直接套用到上海。

## 9. 预算在崩溃与重试下仍然成立

启动访问前事务预留额度，完成后按连接器回执结算；候选入队并不立即消耗详情额度。真正执行详情动作前再次检查缓存，因为另一个查询或前一轮动作可能已经补齐它。

队列动作保存稳定 ID、尝试序号、预留额、开始时间和回执。来源身份限制同一来源的活动详情动作；人工点开补详情和后台补全共用这一约束及计划预算，避免重复请求。

浏览器访问与本地数据库提交不能形成一个原子事务。访问成功后程序崩溃而回执尚未落库时，不能保证访问恰好发生一次，也不能直接释放额度重跑：先核对运行快照、日志及已有资料，无法确认的保留为「结果未知」。其预留额度继续占用本轮可用预算，除非可靠参考资料证明访问没有发生；后续决定重试时另计一次尝试，展示可能重复访问。

暂停先阻止新动作启动，再请求停止活动动作；已发出的访问仍计成本。排队、运行、需要人工处理和未知结果分别展示，不用「停止」掩盖正在结束的访问。时间上限约束新动作启动，活动访问使用有限超时并记录实际结束时间，不能声称页面导航能在截止时刻立即中断。

新增验收场景：

- 两个查询同时给同一来源排详情，只有一个活动动作；晚启动动作命中刚写入的缓存。
- 访问后、回执落库前崩溃，恢复时保留未知状态和预留额度，不静默重试或重置预算。
- 交换查询执行顺序，累计新增数量不变，调度不会仅因首次发现归属变化就判定词语优劣。
- 已审核样本集中于热门岗位族时，其他岗位族显示样本不足，仍保留探索机会。
- 本轮预算不足以覆盖全部城市和岗位族时，展示实际未探索范围，后续轮转能够推进。

## 最小落地边界

首期使用现有数据库保存队列、身份、命中与成本回执，复用现有收件箱；不为规划器新增消息中间件、向量库或独立服务。优先打通一个具备准确计数能力的连接器，再验证另一平台的能力差异。只有实测数据足以解释收益变化时，才增加自动调权。
