# P2｜跨岗位 JD 需求统计与比较

## 使用入口

左侧「分析与准备 → JD 需求画像」是新增的统计页面，与原「能力情报」区别：

- 「能力情报」仍基于已经绑定的岗位技能标签；
- 「JD 需求画像」基于 **P1 的 job_requirements**，仅把人工确认（confirmed）且仍与最新 JD/资格条件版本一致的记录计入可信统计。

必须先通过岗位 JSON → AI 提取 → 要求审核流程形成有效数据。**没有人工确认的数据时显示零覆盖，不能解释为岗位没有这些要求。**

## 口径

1. 基础样本为当前筛选出的独立岗位数，筛选支持岗位或企业或 JD 关键词、岗位方向、企业档位、岗位优先级、城市和岗位核验状态。
2. 覆盖岗位数为至少存在一条*有效*人工确认 JD 要求的独立岗位数；分母仍是所有筛选岗位，包括没有做 JD 结构化提取的记录。
3. 技能频率只纳入 `technical_skill`、`product_skill`、`research_skill` 类型且 `option_logic=single` 的要求。
4. **同一岗位对同一规范化技能最多计一次**；强度按 must > bonus > mentioned > unknown 保留最明确的一档。同一企业下的不同独立岗位可分别计数，同时展示涉及企业数。
5. `option_logic=any_of/all_of` 独立放在「组合要求」中，不能错误拆成多个硬性技能。
6. 已变更 JD/资格条件使来源哈希过期的旧要求，无论此前是否确认，都不纳入当期统计；返回「过期要求」「受影响岗位」供重新分析。
7. AI 待审核（pending）默认不显示；用户勾选后在**单独的表格**展示，不会与已确认频率求和。
8. 方向、企业档位、岗位优先级比较按分组内全部岗位作为分母，额外显示每组最常见的五项已确认技能（各自独立岗位数）；不同组的岗位量和覆盖度不一致，不可只按绝对值推断岗位要求差异。

## 原文追溯

点击任一技能，浏览器通过 `GET /api/requirements/stats/evidence` 获取岗位 ID、企业、方向、企业档位、明确程度、逐字原文摘录、数据包 ID 等，提供每 50 条分页。每项可以进入原岗位档案核对完整 JD。

## 手动技能同义词

通过「技能别名词表」设置*确实等价*的别名，例如「工具调用 → Tool Calling」；不能把 RAG 与 Agent 开发等不同能力强行合并。

- 使用 `POST /api/requirements/stats/aliases` 添加别名。
- `GET /api/requirements/stats/aliases` 查询当前映射；`DELETE /api/requirements/stats/aliases?alias=...` 删除。
- 禁止链式映射或同义词互相循环。
- 不重写原始 JD、确认记录、技能参考资料或优先级；映射仅在统计时应用。
- 每次增删在 `skill_alias_events` 写入审计事件，响应携带 `alias_revision` 和当前 `alias_mappings`。

## JSON 报告

页面「导出统计 JSON」下载统计结果，包括统计范围、已选岗位 ID、当时的技能归一映射、映射版本、覆盖率口径、分组对比、技能逐岗位汇总与组合要求。它**不含完整 JD**，原文参考资料仍应通过单条技能的参考资料明细/原数据包核对。

输出为本次数据库状态的即时计算结果，不是招聘市场总体估计。样本可能明显偏向目标城市、关键词与已收藏企业；未确认记录和未导出的 JD 不属于可信结论。

## 开发实现

- `app/db.py`：数据库 Schema 13，新增 `skill_aliases`、`skill_alias_events`，原有记录不迁移、不覆盖。
- `app/requirement_stats.py`：统计、参考资料追溯与别名维护 API，避免在 `app/main.py` 中复制冗长 SQL。
- `static/app.js` 与 `static/index.html`：新增页面、手动过滤、参考资料弹窗和归一管理。
- `tests/test_requirement_stats.py`：统计分母、跨岗位/企业去重、各档位对比、待审数据隔离、过期 JD、别名和原文追溯。

## 不在本阶段

P2 不自动评估用户的胜任力，不自动修改岗位优先级、不自动给招聘状态打标签，也不自动推荐课程。P3 才将已确认技能需求与个人项目/实习参考资料关联。
