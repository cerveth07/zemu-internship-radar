# 检索与逐条入库流程升级

## 实施顺序

| 项目 | 本轮实现 |
| --- | --- |
| 本次结果隔离 | SQLite 持久保存批次、搜索条件、task ID、run ID、结果关联；查询时校验任务归属。再次命中的历史岗位也计入，沿用缓存 JD 并标明。 |
| 自动展示 | 任务完成、部分失败或停止后自动同步本次结果。同步游标与资料关联事务提交，重复同步安全；历史库同步移至折叠工具。 |
| 条件限定 | 常用城市勾选、自定义城市、多关键词、1–3 页、真实的仅实习筛选。记住公开搜索条件，批次名称自动生成，主按钮直接创建批次并预览检索。 |
| 连续审核 | 左列表右详情；显示城市、薪资和 JD；本地文字筛选；保存草稿、入库并查看下一条、跳过、不感兴趣及恢复。薪资、时长、出勤原文随人工确认入库。 |
| 状态恢复 | 区分服务、浏览器及 BOSS 页面准备状态；有限重试；重新进入恢复当前任务；停止对应只读任务保留已保存结果。启动拒绝与响应超时区别处理。 |
| 资料可信度 | 来源链接、观察时间、缓存 JD 提示、已有岗位/JD 变化标记与缺 JD 提示；不把观察时间或非空 JD 当成仍在招聘或完整参考资料。 |

## 日常流程

填写关键词及城市 → 检索 BOSS 岗位 → 核对预览并启动 → 自动显示本次结果 → 筛选/查看 JD → 逐条确认入库。

薪资、出勤和实习时长目前采用**结果原文筛选**，不是平台端数值范围搜索。核对表单保留原文；没有信息时留空。

独立 Chrome 登录状态保存在本机专用目录。BOSS 页面已连接不代表登录已确认；出现登录或验证码要求，请在该窗口处理。

## 实现与故障边界

- 新运行不通过历史数据库时间差或关键词猜测结果。BossHunter 原生 `collected_job_ids` 仅包含新增岗位；自有启动兼容层观察实际候选以保留重复命中。
- 上游源码保持原样，兼容层只扩展本机 API 和侧库。升级上游版本后需重新验证 processor/helper 接口；不兼容时明确停止，不回退成历史库混合结果。
- 在上游同一锁内应用搜索条件、预检、保存配置并开始 `collect`。预检拒绝不会保存新配置或发起任务。
- 全局活跃搜索的数据库约束防止多个 Radar 窗口重复启动。响应超时时标记待确认，不自动重发；只在上游没有活动任务时允许解除等待。进程崩溃遗留的启动等待需超过 90 秒才可解除。
- 不同批次或同批次新任务的迟到响应不能覆盖当前任务。状态更新和结果同步不重绘正在填写的人工核对表单。
- 旧 15 条待核对资料保留为原批次资料，不虚构它们的任务归属。此次开发检查没有发起新的 BOSS 平台检索。
